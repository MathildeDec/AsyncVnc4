# Session 02 — 2026-09-02

## Mise à jour 2026-09-02 : `send_qemu_extended_key_event()` vérifié contre le code source QEMU officiel

Cette session a levé le principal doute qui pesait sur ce patch : le
format vient désormais d'une lecture fraîche du code source QEMU
lui-même (`github.com/qemu/qemu`, fichier `ui/vnc.c`, commit
`a925240509d1b4b656cc480f1cc79ba4d7c8bc08`, branche `master`, récupéré
via `raw.githubusercontent.com` dans ce sandbox), et non plus de
mémoire. Fonctions côté serveur lues : `protocol_client_msg()`
(dispatch du message-type 255 puis du submessage-type 0) et
`ext_key_event()` (traitement une fois décodé). Cette extension n'étant
documentée dans aucune RFC RFB, le code source QEMU est la seule source
faisant foi — même niveau de rigueur que les vérifications RFC des
autres patches, adapté au fait qu'il n'existe pas de RFC ici.

Confirmé ligne par ligne dans `ui/vnc.c` :
- message-type 255 (`VNC_MSG_CLIENT_QEMU`), submessage-type 0
  (`VNC_MSG_CLIENT_QEMU_EXT_KEY_EVENT`)
- down-flag en **U16** (`read_u16(data, 2)`) — exactement le point que
  ce fichier signalait jusqu'ici comme le plus probable à corriger ; il
  s'avère en réalité correct
- keysym en U32 (`read_u32(data, 4)`), puis keycode en U32
  (`read_u32(data, 8)`), dans cet ordre
- network byte order (big-endian) pour les deux, confirmé en lisant
  l'implémentation même de `read_u16()`/`read_u32()`
  (`(data[offset] << 8) | data[offset+1]`, etc.)
- 12 octets au total, confirmé par `if (len == 2) return 12;` dans
  `protocol_client_msg()`

**Conclusion : l'implémentation de `asyncvnc2.py` était déjà exactement
conforme — aucune ligne de code modifiée.** Vérifié en plus octet par
octet dans ce sandbox (exécution réelle, pas juste relecture) contre 3
messages reconstruits à la main d'après cette lecture de source, dont
des valeurs hautes de bornes U32 (ex. keycode proche de `0xdeadbeef`) :
les 3 correspondent exactement, octet pour octet.


## Le point à ne PAS considérer comme fiable sans test réel — état après cette session

Grâce à la vérification ci-dessus, il ne reste plus aucun format de
message non vérifié contre une source faisant autorité parmi les
patches documentés dans ce fichier. Deux points restent malgré tout non
testés contre un **vrai serveur en fonctionnement** (leur format, lui,
est vérifié) :

**`send_qemu_extended_key_event()`** — format désormais vérifié contre
le code source QEMU officiel (section ci-dessus), mais toujours pas
contre un authentique serveur QEMU/Proxmox. Si la connexion se coupe
après négociation du pseudo-encodage `QEMU_EXTENDED_KEY_EVENT`, le
format lui-même n'est plus le suspect principal (il est confirmé) —
regarder plutôt du côté du séquencement ou d'une interaction avec une
autre partie du protocole. Capturer le trafic (Wireshark, filtre RFB)
reste la méthode recommandée pour comparer si besoin.

Le patch xvp de cette session est dans une situation similaire — le
format vient d'une lecture fraîche de la spec RFB officielle
(`rfbproto.rst`), pas de mémoire — mais comme pour QEMU, aucun serveur
supportant réellement xvp n'était disponible dans ce sandbox pour un
test de bout en bout. Le point le plus probable à vérifier en premier
si un vrai serveur ne réagit pas comme attendu : que le serveur envoie
bien un `XVP_INIT` juste après avoir reçu le pseudo-encodage `Enc.XVP`
dans `SetEncodings` (et pas seulement après une première
`FramebufferUpdateRequest`) — TigerVNC est un bon serveur de test, il
supporte xvp côté serveur.

`listen()` (reconnexion inversée) n'a, elle, aucun format de message à
risque : le protocole RFB après connexion est identique au mode
normal, déjà couvert par les vérifications ci-dessus. Le seul point non
testé ici est le comportement en conditions réelles à travers un vrai
NAT/pare-feu (le cas d'usage principal de la fonctionnalité) — le
sandbox ne peut tester qu'en loopback, ce qui valide la mécanique
(accept, handshake, libération du listener) mais pas la traversée
réseau réelle.

Le repli de version de protocole non plus n'a pas de format à risque
(entièrement issu de la RFC officielle, y compris les différences 3.3/
3.7 en Appendix A) et a été vérifié avec 7 scénarios réels bout en
bout — mais aucun de ces scénarios n'implique un authentique serveur
3.3 physique (seulement des scripts qui *imitent* le comportement 3.3
tel que décrit par la RFC). Si un vrai vieux serveur 3.3 se comporte
différemment de la RFC sur un point non documenté, ce serait le point
à examiner en premier — risque jugé faible vu la rigueur de la spec
sur ce point précis, mais pas nul.

Tout le reste du patch (1 à 5, plus `send_set_desktop_size`, xvp,
`listen()` et le repli de version) est vérifié soit contre la RFC RFB
officielle, soit par exécution réelle du code dans ce sandbox — même
niveau de confiance que ton propre travail sur Tight/Hextile/ZlibHex.


## Mise à jour 2026-09-02 : VeNCrypt (security type 19, sous-types TLSNone/TLSVnc)

Ce patch lève la case « ⚠️ Haute » qui figurait jusqu'ici en tête des
« Prochaines étapes suggérées » de `features.md`. Portée volontairement
limitée aux deux sous-types VeNCrypt dits « anonymes » — `TLSNone` (257,
aucune authentification après la TLS) et `TLSVnc` (258, VNC
Authentication standard après la TLS) — qui sont ceux qui correspondent
à la formulation « TLS anonyme » de `features.md`. `X509None`/`X509Vnc`
restent non implémentés : ils demanderaient un vrai certificat CA à
vérifier, ce qui suppose de faire remonter ce certificat jusqu'à
l'appelant (`connect()`/`listen()`) — rien ne le permettait avant ce
patch, et l'ajouter sans un vrai cas d'usage aurait été deviner une API.

**VeNCrypt n'a jamais été intégré à la RFC 6143 elle-même**, mais figure
bien aujourd'hui dans la spec communautaire qui la complète,
`rfbproto.rst` du dépôt `rfbproto/rfbproto`
(<https://github.com/rfbproto/rfbproto/blob/master/rfbproto.rst>,
section 7.2.4 « VeNCrypt ») — contrairement à ce qu'indiquait la
première version de cette section, écrite avant d'avoir vérifié cette
spec communautaire à jour et se fiant uniquement au tout premier
brouillon de spec, un patch de format RST posté sur la liste
`tigervnc-rfbproto` en 2010 par l'auteur du projet VeNCrypt lui-même
(<https://www.mail-archive.com/tigervnc-rfbproto@lists.sourceforge.net/msg00256.html>).
**Ce brouillon de 2010 et la spec communautaire actuelle divergent sur
un point précis, et cette divergence a été débusquée et corrigée dans
cette même session** — voir le paragraphe dédié plus bas
(« Divergence trouvée et corrigée »). Cette source confirme au passage,
comme effet de bord, que le type de sécurité 19 (VeNCrypt) et le type
18 (« TLS », plus ancien et obsolète, listé séparément dans
`features.md`) sont bien deux mécanismes distincts.

**Déroulé du patch** (voir `_vencrypt_negotiate()` dans `asyncvnc2.py`
pour le détail commenté ligne par ligne) : après sélection du type de
sécurité 19, négociation de version VeNCrypt 0.2 (seule version
documentée — 0.1 n'a jamais été implémentée nulle part d'après l'auteur
de la spec lui-même), lecture de la liste de sous-types offerts par le
serveur, sélection de `TLSVnc` si disponible sinon `TLSNone`, puis
bascule effective de la connexion TCP déjà établie vers TLS (même socket,
pas de nouvelle connexion) via `_start_tls_client()`. Si le sous-type
choisi est `TLSVnc`, le code se contente de positionner `auth_type = 2`
pour retomber dans le bloc « VNC authentication » déjà existant, qui
s'exécute alors sur le flux désormais chiffré — pas de code dupliqué.
Dans tous les cas, la lecture du `SecurityResult` final quelques lignes
plus bas (déjà existante, commune à tout type de sécurité RFB 3.7/3.8)
s'applique sans changement.

**Divergence trouvée et corrigée : l'accusé de réception qui suit le
choix du sous-type.** En rédigeant ce patch, une première vérification
n'a porté que sur le brouillon de 2010 ci-dessus, qui décrit ici un
`U32` de statut (0 = OK) suivi, en cas d'échec uniquement, d'une chaîne
de raison longueur-préfixée (`U32` longueur + octets). Une relecture de
la spec communautaire *actuelle* (`rfbproto.rst`, section « Subtypes
with TLS or X509 prefix ») a montré un texte différent : « the server
then sends **a one byte response**... Non-one value means failure ».
Pour trancher entre les deux, direction le code source de
l'implémentation de référence : `CSecurityTLS::processMsg()` dans
`common/rfb/CSecurityTLS.cxx` de TigerVNC lit très exactement
`if (is->readU8() == 0) throw protocol_error(...)` juste avant
d'initialiser la session GnuTLS — **un seul octet, 0 = échec, non-zéro
= succès, aucune chaîne de raison**. C'est ce format à un octet,
confirmé par l'implémentation qui fait référence en pratique, qui est
implémenté dans `asyncvnc2.py` (et non le brouillon de 2010) ; l'ancien
format `U32` aurait désynchronisé la lecture d'un octet dès la première
vraie connexion (les 3 octets suivants auraient été lus comme le début
de la poignée de main TLS elle-même, provoquant un échec de handshake
TLS incompréhensible sans regarder le code). Erreur détectée avant
livraison, pas après — mais elle illustre bien pourquoi croiser plusieurs
sources (spec + implémentation de référence) reste nécessaire même
quand une spec existe déjà, VeNCrypt n'étant formellement décrit nulle
part avec la même autorité qu'une RFC.

**Le point technique le plus délicat : upgrader une connexion asyncio
déjà établie vers TLS, en place.** `asyncio.StreamWriter` n'expose aucun
`start_tls()` public — la façon documentée de faire est
`loop.start_tls()`, qui remplace le transport sous-jacent d'un protocole
déjà en place. Vérifié par lecture du comportement réel (pas seulement de
la documentation) : `loop.start_tls()` appelle en interne
`protocol.connection_made(nouveau_transport)`, et
`StreamReaderProtocol.connection_made()` réagit à cet appel en rappelant
`stream_reader.set_transport(nouveau_transport)` sur le **même** objet
`StreamReader` que celui déjà utilisé par le code appelant — le reader
existant continue donc à fonctionner sans qu'on ait besoin d'y toucher.
Seul le `StreamWriter` doit être reconstruit (il se lie à un transport
précis à la construction et ne peut pas en changer lui-même) : voir
`_start_tls_client()`, qui reconstruit un `StreamWriter` autour du
nouveau transport TLS en réutilisant le même reader/protocole/event
loop. `Client.create()` réaffecte ensuite ses variables locales
`reader`/`writer` vers ce nouveau couple — tout le reste de la méthode
(lecture du `SecurityResult`, `ClientInit`/`ServerInit`, etc.) continue
de fonctionner sans changement puisqu'il ne manipule que ces deux
variables, jamais le transport directement.

**Vérifié par exécution réelle, pas juste relu :** un faux serveur
VeNCrypt complet (ProtocolVersion, liste de sécurité `[19]` seul —
aucun repli possible sur 1/2/33 —, négociation de version 0.2,
liste de sous-types, accusé TLS à un octet dans son format corrigé
(voir ci-dessus), bascule TLS côté serveur avec un certificat
auto-signé généré par `openssl req -x509`, puis `SecurityResult` /
`ClientInit` / `ServerInit`) tourne sur un vrai socket TCP loopback dans
ce sandbox face à `Client.create()` non modifié (le même code
qu'utilise `connect()` en production) ; testé pour les deux sous-types
`TLSNone` et `TLSVnc` (ce dernier avec un vrai challenge/réponse DES
vérifié côté serveur de test), et le `Client` obtenu est vérifié
utilisable de bout en bout (dimensions et nom de bureau du `ServerInit`
fabriqué lus correctement dans les deux cas). Non-régression vérifiée en
plus : un serveur qui offre `[None, VeNCrypt]` (au lieu de VeNCrypt
seul) continue de faire choisir « None » au client exactement comme
avant ce patch — voir plus bas pourquoi.

**Choix délibéré de priorité : VeNCrypt (19) en dernier dans la liste de
préférence de sécurité**, après Apple ARD (33), None (1) et VNC
Authentication (2) — alors qu'on pourrait argumenter qu'un transport
chiffré de bout en bout devrait plutôt être préféré à une authentification
en clair. Raison : 33/1/2 sont des chemins déjà éprouvés (dont deux
testés par exécution réelle ailleurs dans ce fichier), alors que
VeNCrypt vient d'être ajouté et n'a jamais été testé contre un vrai
serveur. Le placer en dernier garantit qu'un serveur qui proposait déjà
33/1/2 en plus de 19 se comporte **exactement comme avant ce patch** —
seul un serveur qui n'offre QUE le type 19 (auparavant un échec sec,
`unsupported auth types`) bénéficie de ce patch. Si VeNCrypt est un jour
vérifié contre un vrai serveur, cet ordre de préférence mériterait d'être
reconsidéré (le chiffrement de toute la session, pas seulement des
identifiants, est un argument de sécurité réel).

**Nouveau paramètre `ssl_context: Optional[ssl.SSLContext] = None`** sur
`Client.create()`/`connect()`/`listen()` — purement additif, en dernière
position, ne casse aucun appel existant (positionnel ou par mot-clé).
Quand `None` (le défaut) et que le sous-type choisi est `TLSNone`/`TLSVnc`,
un contexte TLS est construit automatiquement avec
`check_hostname = False` et `verify_mode = ssl.CERT_NONE` — c'est le
comportement correct par défaut pour ces sous-types « anonymes »
puisqu'il n'existe par construction aucune CA contre laquelle valider le
certificat auto-signé/éphémère du serveur (c'est précisément le sens
d'« anonyme » ici). Un appelant qui voudrait un jour brancher
`X509None`/`X509Vnc` pourra passer son propre `ssl_context` — mais la
sélection de sous-type elle-même n'accepte encore que `TLSNone`/`TLSVnc`
(voir plus haut).

**Ce qui reste à vérifier avant un usage en production** : comme pour
xvp et QEMU Extended Key Event, aucun vrai serveur supportant VeNCrypt
n'était disponible dans ce sandbox — seul un faux serveur fabriqué à la
main a pu être testé. TigerVNC (configuré pour n'offrir que le type 19)
ou un RealVNC Enterprise seraient de bons candidats pour ce test.


## Mise à jour 2026-09-02 : nettoyage de style partiel (sous-ensemble sûr de `ruff check`)

Tâche indépendante de tout patch fonctionnel (aucun comportement changé),
issue de la case « 🟢 Faible » de `features.md` § « Prochaines étapes
suggérées ». Objectif : appliquer *seulement* les signalements `ruff
check` (règles par défaut, pas `--select ALL`) qui ne posent aucune
question de compatibilité Python, et documenter explicitement ce qui
reste volontairement non fait plutôt que de tout corriger d'un coup.

**Constat de départ.** `ruff check` (règles par défaut) trouve 51
signalements sur le fichier tel qu'il était en début de session (46
`UP006`/`UP035`/`UP045` — modernisation des annotations de type — plus 5
autres). Ce chiffre n'est pas comparable au « 45 sur 44 » de la section
précédente, qui utilisait `--select ALL` (règles étendues) sur une
version antérieure du fichier, avant l'ajout de xvp/`listen()`/repli de
version.

**Appliqué** (6 signalements, zéro changement de comportement) :
- `I001` — tri des imports (fix marqué « sûr » par ruff) ;
- `C400` — dans `_update_palette()`, générateur → liste en compréhension ;
- `C408` — dans `Video.process_xrle()`, `list()` → `[]` ;
- `SIM102` (×2) — deux `if` imbriqués fusionnés avec `and`, dans
  `Client.process_extended_desktop_size()` et `Client.screenshot()` ;
- `RUF013` — l'`Optional` implicite de `_update_palette(..., palette:
  list = None)` rendu explicite (`Optional[list]`), en suivant la
  convention déjà utilisée par les 28 autres `Optional[...]` du fichier
  plutôt que la correction `X | None` que ruff suggère par défaut (voir
  plus bas pourquoi `X | None` n'est délibérément pas utilisé ici).

**Vérifié par exécution réelle, pas juste relu :**
- `ruff check` réexécuté après coup : les 6 signalements ciblés ont
  disparu (`ruff check --select I001,C400,C408,SIM102,RUF013` → « All
  checks passed! ») ; seul effet de bord attendu, le passage à
  `Optional[list]` fait apparaître un *nouveau* signalement `UP045` sur
  cette même ligne — cohérent, ce nouvel `Optional[...]` rejoignant
  volontairement le même groupe non traité que les 27 autres (46

**Délibérément PAS appliqué** (46 signalements restants, tous
`UP006`/`UP035`/`UP045`) :
- `UP006`/`UP035` (`Dict`/`List`/`Set`/`Tuple` → `dict`/`list`/`set`/

  `key_codes: Dict[str, int] = {}` au niveau module) — sûr seulement à
  partir de Python 3.9 (PEP 585) ;
- `UP045` (`Optional[X]` → `X | None`) — sûr seulement à partir de
  Python 3.10 pour des annotations évaluées au runtime comme ici (pas de
  `from __future__ import annotations` dans ce fichier) ;
- `ruff format` complet (reformatage global : guillemets simples →
  doubles partout, chaque collection multi-éléments éclatée sur
  plusieurs lignes, etc.) — testé en `--diff` à titre exploratoire
  (~1500 lignes de diff sur un fichier de 2028 lignes), bien trop large
  pour être vérifié ligne par ligne dans la même réponse, et change des
  choix de mise en forme visiblement délibérés (ex. l'alignement manuel
  de `video_modes`).

Ce paquet ne fixe aucune version Python minimale (pas de
`pyproject.toml` ni `setup.py` livré avec ce fichier unique) : décider
d'abandonner la compatibilité < 3.9/3.10 n'est donc pas une simple
question de style, c'est une décision produit qui revient à qui déploie
`asyncvnc2.py` — pas quelque chose à trancher unilatéralement dans un
nettoyage de style. Si la version Python minimale visée est confirmée
≥ 3.10, les 46 signalements restants deviennent alors un nettoyage sûr
en une seule passe (`ruff check --fix --unsafe-fixes` couvre
l'essentiel) ; `ruff format` complet, lui, reste de toute façon une
décision de mise en forme à part entière, quelle que soit la version
Python visée.
