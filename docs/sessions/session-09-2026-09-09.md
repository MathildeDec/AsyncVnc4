# Session 09 — 2026-09-09

## Session 2026-09-09 : `send_qemu_extended_key_event()` — premier test réel contre un vrai QEMU, trois comportements réels découverts

Prochain point « 🟠 Moyenne » de la liste « Prochaines étapes
suggérées » : confirmer le comportement réel d'un serveur QEMU/Proxmox
face à ce message (format déjà vérifié le 2026-09-02 contre le code
source officiel, mais jamais exercé contre un vrai serveur). Aucun
Proxmox disponible dans ce sandbox -- utilisé à la place
`qemu-system-x86_64` 8.2.2 (paquet Ubuntu, installé via `apt`), qui
partage le même code serveur VNC (`ui/vnc.c`) que Proxmox pour sa
console : la couverture obtenue ici s'applique donc directement à
Proxmox, même si Proxmox lui-même (au-delà de la couche `ui/vnc.c`
commune) n'a pas été essayé.

**Méthodologie retenue : un secteur de boot BIOS fait main plutôt
qu'un OS complet.** But du test : obtenir une preuve *comportementale*
sans ambiguïté (pas juste « aucune exception levée ») que le caractère
demandé arrive réellement jusqu'au clavier émulé du guest. Un OS
complet (image disque, noyau) aurait ajouté une dépendance lourde et
une couche d'interprétation supplémentaire (pilote clavier de l'OS,
layout éventuel) sans rien apporter pour ce test précis. À la place,
16 lignes d'assembleur x86 réel-mode (`nasm`, installé via `apt`) :
affiche `READY:`, puis boucle indéfiniment sur *lire une touche via
BIOS INT 16h/AH=00h, l'afficher via INT 10h/AH=0Eh (teletype)*. Une
lecture BIOS INT 16h dépend uniquement du contrôleur clavier PS/2
émulé par QEMU -- aucune couche OS/pilote entre les deux, donc un test
aussi direct que possible du chemin serveur VNC -> clavier virtuel.
Une trentaine de lignes d'assembleur x86 réel-mode (moins de 50 octets
de code+données utiles une fois assemblées), le reste du secteur
n'étant que du remplissage à zéro imposé par le format (512 octets
fixes, signature `55 AA` finale).
Assemblé en secteur de boot brut de 512 octets (signature `55 AA`),
démarré avec `qemu-system-x86_64 -m 32 -drive file=boot.img,format=raw
-vnc 127.0.0.1:1 -monitor none -serial none -parallel none -display
none -no-reboot` (pas de mot de passe VNC : authentification déjà
massivement couverte ailleurs dans ce fichier, hors sujet ici). Preuve
capturée avec le propre `screenshot()` de `asyncvnc2.py` (le même code
que celui livré), comparaison de pixels avant/après chaque envoi --
donc chaîne complète client patché -> vrai QEMU -> clavier PS/2 émulé
-> BIOS guest testée de bout en bout, pas seulement la construction du
message côté client.

**Test de référence : cas nominal.** `send_qemu_extended_key_event(down=True,
keysym=0x31, keycode=2)` puis `down=False` (touche « 1 », keysym et
keycode cohérents, sans ambiguïté de casse) : `READY:` devient
`READY:1` à l'écran, confirmé par capture avant/après (45 pixels
modifiés, bbox cohérente avec un seul glyphe). Rejoué avec succès pour
plusieurs autres touches cohérentes au long de la session (`2`, `s`,
`e`, `4`) en faisant boucler le secteur de boot (deuxième version,
`jmp loop_key` au lieu de `jmp hang`, pour enchaîner plusieurs touches
dans la même session sans redémarrer QEMU à chaque fois) : le cas
nominal fonctionne à chaque fois, exactement comme attendu.

**Constat 1 : `keycode=0` est silencieusement ignoré, pas de repli sur
le keysym seul.** `keysym=0x33` (« 3 »admis) avec `keycode=0` : 0 pixel
modifié à l'écran, aucun caractère reçu. Reconfirmé indépendamment avec
un keysym différent (`0x7A`, « z »), attente portée à 1s par prudence
(écart de timing exclu) : même résultat, toujours rien. Un appelant de
cette fonction doit donc toujours fournir un vrai keycode evdev non
nul -- l'espoir d'un repli automatique sur le keysym seul en cas de
keycode indisponible est infondé, au moins pour ce QEMU 8.2.2.

**Constat 2 : un layout clavier explicite côté serveur (`-k <layout>`)
fait perdre tout l'intérêt de l'extension.** Repéré en lisant le vrai
code source (`github.com/qemu/qemu`, `ui/vnc.c`, fonction
`ext_key_event()`) :
```c
static void ext_key_event(VncState *vs, bool down,
                          uint32_t sym, uint32_t keycode)
{
    /* if the user specifies a keyboard layout, always use it */
    if (keyboard_layout) {
        key_event(vs, down, sym);
    } else {
        do_key_event(vs, down, keycode, sym);
    }
}
```
Un `-k <layout>` explicite au lancement de QEMU bascule *tout*
événement clavier étendu sur `key_event(vs, down, sym)` -- le chemin
keysym-seul, strictement identique à celui du vieux message RFB
`SetKeyEvent` non étendu, en ignorant totalement `keycode`. Confirmé
empiriquement, pas seulement lu : QEMU relancé avec `-k en-us` en plus
des mêmes options, `keycode=0` + `keysym=0x31` (« 1 ») -- qui ne
produisait rien sans `-k` (constat 1 ci-dessus) -- produit cette fois
bien `1` à l'écran (63 pixels modifiés, caractère confirmé par capture
zoomée), la preuve la plus directe que `keycode` est bien ignoré dans
ce mode. **Conséquence pratique pour tout appelant (`pluginvnc2` ou
autre)** : dès que la cible QEMU/Proxmox a un layout clavier configuré
côté serveur -- un cas courant en dehors d'un clavier US, donc
plausible en production --, tout l'avantage de
`send_qemu_extended_key_event()` par rapport au simple `SetKeyEvent`
disparaît silencieusement, sans que ce client n'ait aucun moyen de le
détecter à l'avance (le serveur ne signale pas si `-k` est actif).

**Constat 3 : keysym/keycode délibérément incohérents -- résultat
observé, mécanisme non confirmé à 100 %.** Deux essais, sans `-k` :
`keycode=30` (touche physique KEY_A) + `keysym=0x42` (« B », majuscule
sans rapport) -> caractère obtenu : **`A`** majuscule (ni `a` seul, ni
`B` seul). `keycode=32` (touche physique KEY_D) + `keysym=0x24` (« $ »,
symbole majuscule sans rapport) -> caractère obtenu : **`d`**
minuscule (ni `D`, ni `$`). Hypothèse la plus probable, cohérente avec
ces deux essais indépendants : un keysym ASCII majuscule A-Z (`'B'`
ici, pas `'$'`) déclenche une touche Shift synthétisée côté serveur,
appliquée à la touche physique désignée par `keycode` -- comportement
qui existe bel et bien quelque part dans ce code, comme le montre le
chemin non étendu `key_event()` lu au passage dans le même fichier :
```c
if (lsym >= 'A' && lsym <= 'Z' && qemu_console_is_graphic(...)) {
    lsym = lsym - 'A' + 'a';
}
keycode = keysym2scancode(vs->vd->kbd_layout, lsym & 0xFFFF, ...);
do_key_event(vs, down, keycode, sym);  /* le sym ORIGINAL (pas lsym) */
```
`do_key_event()` reçoit bien le `sym` d'origine (majuscule), pas la
version mise en minuscule -- cohérent avec l'idée que la détection
« ce sym est-il une majuscule A-Z » vit dans `do_key_event()` lui-même
et s'applique donc aussi au chemin étendu, indépendamment de l'origine
du `keycode`. **Cette hypothèse n'a toutefois PAS été confirmée en
lisant l'intégralité de `do_key_event()`** (fonction longue, coupée
dans les extraits consultés) -- seulement les deux essais empiriques
ci-dessus, tous deux cohérents avec elle. Conclusion pratique retenue,
indépendante du mécanisme exact : ne jamais compter sur un keysym et
un keycode incohérents pour obtenir un résultat prévisible -- toujours
les garder mutuellement cohérents, comme le ferait un vrai clavier
physique (exactement l'usage pour lequel cette extension est conçue,
voir docstring de la fonction, mise à jour en conséquence).
