## Décision : type 18 abandonné, MSLogonII implémenté

**Type de sécurité 18 (« TLS » isolé) — confirmé infaisable
proprement**, pas seulement « valeur incertaine » comme le disait le
backlog jusqu'ici : sans aucune source documentant son format,
l'implémenter reviendrait à deviner un protocole entier. Ce fichier a
déjà un principe établi de refuser de deviner un format non documenté
(cf. ZYWRLE, où seul le format d'une tuile dans un encodage par
ailleurs bien spécifié restait flou — et le décodeur refuse
explicitement plutôt que de deviner). Le cas du type 18 est encore
plus radical : aucun format du tout n'est publié. Non implémenté.

**SASL (20) — également écarté cette session**, pour une raison
différente : la section dédiée existe bien et est détaillée, mais
décrit un protocole multi-étapes générique dont le nombre d'échanges
dépend du mécanisme choisi par le serveur (`DIGEST-MD5`, `GSSAPI`,
`ANONYMOUS`, etc.). Implémenter ne serait-ce qu'un seul mécanisme
demanderait une bibliothèque SASL tierce (`cyrus-sasl`, souvent une
infrastructure Kerberos pour `GSSAPI`) — périmètre bien au-delà d'une
seule tâche, et la confirmation obtenue de l'utilisateur portait sur
l'idée générale « investir dans le backlog incertain », pas sur SASL
spécifiquement (qui reste, lui, un investissement de nature différente
— une nouvelle dépendance et potentiellement une infra Kerberos, pas
seulement du temps de développement).

**MSLogon original (distinct de MSLogonII) — également écarté** :
contrairement à MSLogonII, il n'a pas de section dédiée dans
`rfbproto.rst` — même blocage que le type 18.

**Ultra (LZO)** (encodage d'image, pas type de sécurité) — également
écarté : nécessiterait une dépendance de décompression LZO, absente de
la bibliothèque standard Python, pour un encodage spécifique à
UltraVNC sans serveur de référence dans ce sandbox.

**MSLogonII (113) — implémenté**, seul candidat à la fois documenté
en détail et raisonnablement bornable en une session.

## Implémentation

### `_pack_mslogonii_field()` (nouvelle fonction, à côté de `pack_ard()`)

Encode un champ nom d'utilisateur/mot de passe : UTF-8, terminateur
nul, complété d'octets aléatoires jusqu'à la taille de champ demandée
(256 pour le nom d'utilisateur, 64 pour le mot de passe — tailles
fixées par la spec). Même motif que `pack_ard()` (Apple ARD), avec une
taille de champ paramétrable au lieu de la valeur fixe 64 codée en dur
pour ARD. `ValueError` si l'identifiant/mot de passe dépasse la place
disponible (terminateur nul compris), même style d'erreur que
`pack_ard()`.

### Bloc `if auth_type == 113:` dans `Client.create()`

Inséré juste après le bloc VNC Authentication (`auth_type == 2`),
puisqu'il en réutilise directement le bit-reversal DES :

1. Lecture de trois champs `U8[8]` : `generator`, `modulus`,
   `public-value` (dans cet ordre, comme le tableau de la spec) ;
2. Garde-fou `modulus < 2` → `ValueError` (défensif, la spec ne prévoit
   pas ce cas mais une exponentiation modulaire par un modulus non
   défini n'a pas de sens) ;
3. Exposant privé client : un entier aléatoire tiré de 8 octets
   (`os.urandom`), ramené dans `[1, modulus-2]` par modulo — la spec ne
   précise aucune contrainte de génération au-delà de l'exponentiation
   modulaire standard elle-même, donc `pow(base, exp, mod)` natif
   Python suffit (pas de bibliothèque cryptographique dédiée, cohérent
   avec le fait que la spec qualifie déjà cette clé 64 bits de non
   sûre) ;
4. Secret partagé = `pow(server_public, client_private, modulus)`,
   converti en 8 octets big-endian ;
5. Clé DES = bit-reversal du secret partagé, **exactement le même code
   que VNC Authentication** ci-dessus (la spec l'indique explicitement :
   « The DES algorithm used here is the same as the one for VNC
   authentication, which uses the reverse bit order ») ;
6. IV = le secret partagé **tel quel, non inversé** — la spec ne
   mentionne le bit-reversal qu'à propos de la clé, pas de l'IV ;
7. Chiffrement DES-CBC des deux champs (voir choix d'interprétation
   ci-dessous) ;
8. Envoi de `client_public (8 octets) + username_ciphertext (256
   octets) + password_ciphertext (64 octets)`.

Après cet envoi, le flux reprend en clair pour `SecurityResult` et la
suite — pas de wrapper `reader`/`writer` façon VeNCrypt/RSA-AES, la
spec confirme (« After that the server verifies if supplied
credentials are correct and continues with the SecurityResult
message »).

### Ordre de préférence de négociation

`113` ajouté en dernière position du tuple `(33, 1, 2, 19, 129, 5,
113)` : nouveau, jamais testé contre un vrai serveur, et sa clé DH 64
bits est qualifiée par la spec elle-même de cassable « immédiatement »
— n'apporte donc pas de confidentialité réelle contre un attaquant
actif, seulement un nom d'utilisateur en plus de ce que VNC
Authentication (2) offre déjà.

## Deux ambiguïtés de spec tranchées (documentées en commentaire dans le code)

1. **Ordre de lecture des trois champs Diffie-Hellman** : le tableau de
   la spec liste `generator`, `modulus`, `public-value` dans cet
   ordre — lu tel quel, aucune ambiguïté réelle ici, mais noté car
   aucune vérification contre un vrai serveur ne le confirme.
2. **« encrypt the username and password using DES in CBC mode,
   respectively »** : lu comme deux chiffrements CBC indépendants (une
   instance par champ, chacune redémarrant avec le secret partagé
   comme IV), pas un seul flux continu sur les deux champs concaténés.
   La spec ne tranche pas explicitement ce point — seule interprétation
   retenue faute d'un vrai serveur MSLogonII contre lequel vérifier
   laquelle des deux lectures est la bonne.

## Vérification

**Pas de serveur MSLogonII de référence installable dans ce sandbox
Linux** (extension originaire d'UltraVNC/Windows) — même limite déjà
documentée pour MSLogon/MSLogonII/Ultra(LZO) dans ce fichier avant
cette session.

**Round-trip auto-cohérent fabriqué à la main** (script `/tmp/
mslogon_check.py`, non committé — usage ponctuel, comme les
vérifications manuelles faites lors du développement initial de
VeNCrypt/RSA-AES avant la décision de ne pas les tester unitairement) :
un « serveur » recalcule le même secret Diffie-Hellman à partir de la
valeur publique envoyée par le client, dérive la même clé DES
(bit-reversal), déchiffre les deux champs avec le même IV, et compare
au nom d'utilisateur/mot de passe d'origine (accentués et non-ASCII
inclus, `'utilisateur_é_試験'` / `'motdepasse_ç'`). Résultat : identique
dans les deux sens. **Ceci confirme que l'implémentation est cohérente
avec sa propre lecture de la spec, pas qu'elle interopère avec un vrai
serveur MSLogonII** — nuance importante, différente du reste des
vérifications « réelles » de ce fichier.

**Pas de test unitaire committé** dans `test_asyncvnc2.py` : même choix
que pour le reste de VeNCrypt/RSA-AES/Apple ARD (poignée de main
complète volontairement non testée unitairement — `pack_ard()`
lui-même n'a d'ailleurs jamais eu de test dédié, vérifié en relisant
`test_asyncvnc2.py` avant de décider). Seules les fonctions pures comme
les primitives EAX ont ce traitement dans ce fichier.

**Non-régression** : 43/43 tests toujours au vert, `ruff check` et
`ruff format --check` propres après reformatage du nouveau code
(`uv run ruff format asyncvnc2.py test_asyncvnc2.py`).
