# Session 04 — 2026-09-04

## Mise à jour 2026-09-04 : RFB-sur-WebSockets, rôle serveur (`listen(websocket=True)`)

Complète le patch WebSocket de la veille (rôle client, `connect()`) par
son pendant côté serveur, pour la reconnexion inversée à travers un
proxy WebSocket — cas d'usage réel : un serveur VNC distant qui ne peut
initier une connexion sortante qu'en WebSocket (par exemple parce qu'il
se trouve dans un environnement qui ne route que du trafic HTTP/WS
sortant), et qui a donc besoin que notre `listen()` sache accepter une
poignée de main WebSocket entrante plutôt qu'une connexion TCP brute.

**Réutilisation maximale du code déjà écrit et déjà vérifié la veille.**
Seuls deux éléments changent réellement entre les rôles client et
serveur d'une poignée de main WebSocket (RFC 6455 §4) : qui initie la
requête HTTP (`_ws_handshake_server()` la reçoit et y répond, plutôt que
de l'émettre comme `_ws_handshake()`) et le sens du masquage des trames
sortantes (§5.3 : jamais masquées côté serveur, contre toujours côté
client) — d'où le nouveau paramètre `mask: bool = True` sur
`_WebSocketWriter`, `False` uniquement pour le nouveau
`_ws_wrap_connection_server()`. `_ws_pump()` (la boucle de lecture qui
réassemble le flux d'octets RFB à partir des trames WS) n'a, elle,
strictement rien eu besoin de changer : elle démasque déjà
conditionnellement selon le bit de masque de chaque trame reçue, quel
que soit le sens d'établissement de la connexion, donc reste
directement réutilisable telle quelle dans les deux rôles.

**Vérifié par exécution réelle contre un vrai client tiers, pas contre
mon propre code.** `websockets` (bibliothèque Python de référence pour
implémenter un client ou un serveur WebSocket, indépendante de ce
fork — <https://websockets.readthedocs.io/>) a été installée et utilisée
comme client dans ce sandbox : elle se connecte à
`listen(websocket=True)`, joue le rôle du serveur VNC distant (envoie
`ProtocolVersion`/`Security`/`SecurityResult`/`ServerInit` fabriqués à la
main, mais à travers de vraies trames WebSocket produites par
l'implémentation `websockets`, pas par mon propre `_ws_frame()`), et le
`Client` obtenu côté `listen()` est vérifié utilisable de bout en bout
(dimensions et nom de bureau du `ServerInit` lus correctement). C'est un
test plus significatif qu'un aller-retour avec mon propre code : il
vérifie une véritable interopérabilité protocolaire avec une
implémentation WebSocket tierce, dans les deux sens du masquage RFC 6455
(elle masque ses trames sortantes comme l'exige la RFC pour un client,
et accepte les miennes non masquées comme l'exige la RFC pour un
serveur).

Non-régression vérifiée : `listen()` appelé sans `websocket=True` (le
défaut) continue de fonctionner exactement comme avant ce patch, sur un
vrai socket TCP loopback avec un serveur RFB classique jouant le rôle du
"serveur VNC distant" qui initie la reconnexion.

**Ce qui reste non couvert** : un test contre un vrai `websockify` en
topologie "reverse" complète (le proxy relayant une connexion WS
entrante de bout en bout vers notre port d'écoute, plutôt qu'une
bibliothèque cliente WS générique parlant directement à `listen()`) —
`websockify` est conçu pour l'usage inverse (accepter des clients WS et
relayer vers une cible TCP), pas pour initier lui-même une connexion WS
sortante, donc simuler cette topologie précise aurait demandé un script
supplémentaire côté "serveur VNC distant" plutôt que `websockify`
lui-même ; noté en 🟢 Faible dans `features.md`, le risque de format
étant désormais couvert par le test ci-dessus dans les deux sens
(client et serveur RFC 6455).
