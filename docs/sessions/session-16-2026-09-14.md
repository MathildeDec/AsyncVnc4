SecurityTypes - ... (None, VncAuth, Plain, TLSNone, TLSVnc, TLSPlain,

                 RA2ne_256) (default=TLSVnc,VncAuth)

`Plain`/`TLSPlain`/`X509Plain` et `RA2`/`RA2ne`/`RA2_256`/`RA2ne_256`

**Deux nouvelles pistes, un seul choix retenu pour cette session.**
RSA-AES (RA2) est un type de sécurité RFB à part entière, avec son
propre échange de clés RSA — un travail d'implémentation nettement plus
lourd que ce qui suit, hors périmètre d'une seule tâche de session ;
noté dans `features-backlog.md` pour une session future, non traité
ici. VeNCrypt Plain, en revanche, n'est qu'un **troisième suffixe** sur
l'infrastructure VeNCrypt déjà entièrement implémentée et testée
(TLSNone/TLSVnc/X509None/X509Vnc) : après la poignée de main TLS/X.509
déjà en place, il suffit d'envoyer un identifiant et un mot de passe en
clair (sur le flux désormais chiffré) au lieu de rien (`None`) ou d'un
défi DES (`Vnc`). Ampleur du changement très inférieure à RA2 — retenu
comme tâche de cette session.

**Spec.** `rfbproto.rst` (déjà en cache local), section VeNCrypt,
« Plain subtype » : `U32` longueur-identifiant, `U32` longueur-mot-de-passe,
puis les deux chaînes d'octets, dans cet ordre, envoyées après que la
poignée de main TLS/X.509 a réussi. **Vérifié aussi contre le client de
référence** : `CSecurityPlain.cxx` de TigerVNC (`processMsg()`) — mêmes
quatre champs, même ordre, aucun écart.

**Choix d'implémentation.**
- Réutilise les paramètres `username`/`password` déjà acceptés par
  `Client.create()` (jusqu'ici seulement pour l'authentification Apple,
  type 33) — aucun nouveau paramètre sur `connect()`/`listen()`/
  `Client.create()`.
- Encodage UTF-8 : contrairement au mot de passe VNC Auth (Latin-1,
  contrainte par la troncature à 8 octets de la clé DES sous-jacente —
  voir la ligne dédiée dans `features-backlog.md`), Plain n'a aucune
  contrainte de ce type ; UTF-8 est le choix moderne et non ambigu,
  cohérent avec le traitement déjà réservé au texte d'Extended
  Clipboard (session précédente).
- Ordre de préférence étendu à six sous-types : `X509Vnc > X509Plain >
  X509None > TLSVnc > TLSPlain > TLSNone`. Le degré de chiffrement
  d'abord (X509 avant TLS anonyme, choix déjà en place) ; puis, à
  chiffrement égal, « exige une authentification » avant « aucune » ;
  puis, entre les deux méthodes d'authentification, `Vnc` avant
  `Plain` — le défi DES de VNC Auth ne met jamais le mot de passe en
  clair sur le fil, même une fois le TLS retiré, contrairement à Plain
  qui l'expose directement au serveur (sans risque tant que le TLS
  tient, mais un intermédiaire qui terminerait le TLS — un proxy
  d'entreprise, par exemple — le verrait, ce qui ne serait jamais le
  cas avec `Vnc`).
- La branche de code ajoutée dans `Client.create()` n'aliase PAS
  `auth_type` vers `2` (VNC Authentication) comme le fait la branche
  `Vnc` juste au-dessus : le format Plain n'a aucun défi envoyé par le
  serveur, donc rien à réutiliser du bloc VNC Authentication existant —
  l'envoi se fait directement dans cette nouvelle branche,
  `SecurityResult` étant lu ensuite exactement comme pour tout autre
  type de sécurité.

**Test réel contre TigerVNC/Xvnc 1.13.1, dès le départ.** Contrairement
aux quatre autres sous-types VeNCrypt (d'abord vérifiés contre un faux
serveur fabriqué à la main, puis contre un vrai serveur dans une
session ultérieure), Plain a été testé directement contre un vrai
serveur : `SSecurityPlain` de TigerVNC (`common/rfb/SSecurityPlain.cxx`,
lu avant d'implémenter quoi que ce soit) délègue entièrement la
vérification du mot de passe à PAM (`UnixPasswordValidator`) côté
Linux — sans validateur configuré, le serveur refuse même de démarrer
la négociation (`"No password validator configured"`). Un vrai
utilisateur Linux (`useradd`/`chpasswd`) et un service PAM ont donc été
mis en place dans ce sandbox spécifiquement pour ce test
(`-PAMService tigervnc`, réutilisant le fichier `/etc/pam.d/tigervnc`
déjà fourni par le paquet Debian/Ubuntu — `@include common-auth`/
`common-account`), aux côtés de `-SecurityTypes TLSPlain -PlainUsers
<utilisateur>` côté serveur.

Quatre scénarios vérifiés de bout en bout :
1. Identifiant + mot de passe corrects → connexion réussie, dimensions
   et nom de bureau lus correctement.
2. Mot de passe incorrect → `PermissionError: Auth failed` — remontée
   par le code `SecurityResult` déjà existant, entièrement inchangé.
3. Identifiant inexistant → même rejet.
4. Ni identifiant ni mot de passe fournis → `ValueError` levée avant
   tout envoi réseau (même garde-fou que pour l'authentification Apple
   ci-dessus, réutilisé tel quel).

Effet de bord bénin observé en cours de test, sans rapport avec ce
patch : un avertissement `asyncio` (« returning from eof_received() has
no effect when using ssl ») apparaît à la fermeture d'une connexion TLS
refusée — comportement générique d'`asyncio`/`ssl` sur une coupure
abrupte du transport, pas quelque chose que ce patch cause ou peut
éviter.
