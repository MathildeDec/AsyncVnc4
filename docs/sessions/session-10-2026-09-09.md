# Session 10 — 2026-09-09

## Session 2026-09-09 (2) : xvp — test réel contre un vrai TigerVNC/Xvnc, extension non supportée par ce serveur et fermeture de connexion constatée

Dernier point « 🟠 Moyenne » restant de la liste « Prochaines étapes
suggérées » avant ZYWRLE (test de qualité d'image, portée différente) :
tester `send_xvp_shutdown()`/`_reboot()`/`_reset()` contre un vrai
serveur pour confirmer que le format écrit d'après la spec (`rfbproto.rst`,
vérifié octet par octet en sandbox depuis le 2026-09-01) fonctionne
effectivement de bout en bout, comme cela a été fait pour VeNCrypt
(2026-09-08) et l'extension clavier QEMU (2026-09-09, session précédente
le même jour).

**Serveur utilisé : `Xtigervnc`/`Xvnc` 1.13.1**, installé via `apt`
(`tigervnc-standalone-server`, paquet Ubuntu `noble/universe`) dans ce
sandbox — le même logiciel serveur déjà utilisé pour le test VeNCrypt du
2026-09-08. `features-backlog.md` mentionnait jusqu'ici « TigerVNC la
supporte côté serveur » pour xvp, **une hypothèse qui n'avait jamais été
vérifiée** (contrairement à la plupart des affirmations de ce fichier) —
ce test corrige cette hypothèse : voir résultat ci-dessous.

**Protocole de test.** `Xtigervnc :2 -SecurityTypes None -geometry
320x240 -depth 24 -rfbport 5902` (sans authentification, pour isoler le
comportement xvp de toute question d'auth déjà couverte ailleurs dans ce
fichier). Deux scénarios comparés sur ce même serveur, dans la même
session de test, pour un contraste direct :

- **Test A (référence)** : connexion normale via `connect()` (qui
  demande `Enc.XVP` par défaut, inclus dans `Enc.default()`), lecture
  d'une mise à jour, déconnexion propre **sans jamais appeler
  `send_xvp*()`**. Résultat serveur (`Xvnc` log) : `closing ... : Clean
  disconnection` — comportement de référence normal.
- **Test B** : même connexion, puis `await
  client.send_xvp_shutdown(confirm=True)` explicite. Résultat serveur
  (même log, connexion suivante) :
  ```
  SMsgReader:  unknown message type 250
  VNCSConnST:  closing 127.0.0.1::52964: unknown message type
  ```
  Côté client, la lecture suivante (`client.read()`) échoue avec
  `asyncio.exceptions.IncompleteReadError: 0 bytes read on a total of 1
  expected bytes` — la connexion TCP a bien été fermée par le serveur.

**Rejoué deux fois de bout en bout** (deux instances `Xvnc` distinctes,
sur les ports 5901 puis 5902, pour repartir d'un log serveur vierge à
chaque fois) : résultat strictement identique les deux fois, y compris
le même message de log serveur mot pour mot.

**Constat principal : TigerVNC/Xvnc 1.13.1 ne supporte pas xvp.** Aucun
`XVP_INIT` n'a jamais été reçu, y compris après plusieurs
`FramebufferUpdate` (le temps qu'un serveur supportant réellement
l'extension aurait normalement pris pour le confirmer). Ceci corrige
l'hypothèse précédente de `features-backlog.md` : xvp est en réalité une
extension distincte de tout serveur VNC/Xvnc classique — le nom vient du
logiciel tiers `xvp` (« Xen VNC Proxy », `xvpsource/xvp` sur GitHub), un
*proxy* qui se place devant un ou plusieurs vrais serveurs VNC et parle
lui-même cette extension aux clients qui s'y connectent, plutôt qu'une
fonctionnalité qu'un serveur VNC/Xvnc implémenterait nativement. Ce
logiciel `xvp` n'a pas été installé dans ce sandbox pour cette session
(voir « Ce qui reste non couvert » ci-dessous).

**Constat secondaire, plus important pour tout appelant de
`send_xvp()` : un message-type 250 non reconnu ne provoque pas un
silence côté serveur, mais une fermeture de connexion.** La docstring de
`send_xvp()` affirmait jusqu'ici (jamais vérifié avant cette session)
qu'un « serveur sans support xvp ignorera simplement le message, comme
n'importe quel autre type de message qu'il ne reconnaît pas ». **Ce test
réel contredit directement cette affirmation** pour TigerVNC : le
serveur journalise explicitement `unknown message type 250` et ferme la
connexion (`VNCSConnST: closing ... : unknown message type`) — un
comportement générique de ce serveur face à *tout* message-type qu'il ne
reconnaît pas (pas spécifique à xvp), mais qui a une conséquence concrète
et jusqu'ici non documentée : **appeler `send_xvp_shutdown()`/`_reboot()`/
`_reset()` contre un serveur qui ne supporte pas réellement xvp casse la
session RFB entière**, pas seulement la commande xvp elle-même. La RFC
RFB (6143) ne prescrit aucun comportement obligatoire pour un
message-type inconnu côté serveur (silence, fermeture, ou autre — tout
est conforme du point de vue de la spec), donc ce constat est propre à
l'implémentation TigerVNC testée ici, mais il est prudent de supposer
qu'un comportement similaire (fermeture plutôt que silence) est plausible
chez d'autres serveurs.

**Conséquence pratique retenue, docstrings mises à jour en conséquence**
(voir `send_xvp()` et `process_xvp()` dans `asyncvnc2.py`) : ce qui était
présenté comme une simple recommandation de prudence (« un appelant
prudent devrait attendre `xvp_supported == True` ») est reformulé en
précaution nécessaire — sans confirmation préalable via `XVP_INIT`, un
appel à `send_xvp*()` contre un serveur qui ne supporte pas réellement
l'extension risque de fermer la connexion RFB entière, pas seulement
d'échouer silencieusement comme le supposait la documentation
précédente.

**Aucun changement de format binaire.** Le message envoyé par
`send_xvp()` reste exactement les 4 mêmes octets qu'avant cette session
(`bytes([250, 0, _XVP_VERSION, code])`) — ce test ne remet pas en cause
la conformité du format à la spec (déjà vérifiée octet par octet le
2026-09-01), seulement la description du comportement serveur en
l'absence de support. Vérifié par exécution réelle dans ce sandbox :
import réussi, signature de `send_xvp()`/`connect()` inchangée, `dir(asyncvnc2)`
toujours à 66 symboles publics, `ruff check` toujours à 60 signalements
préexistants (aucun nouveau), 13 tests de `test_asyncvnc2.py` toujours au
vert (aucun test automatisé ajouté pour ce scénario — comme pour
VeNCrypt-contre-TigerVNC le 2026-09-08 et QEMU le 2026-09-09, un vrai
serveur externe est nécessaire, hors du moule « aucune nouvelle
dépendance, aucun processus externe » de cette suite ; script de
vérification ad hoc non inclus dans ce zip, comme les autres scripts de
vérification contre un vrai serveur des sessions précédentes).

**Ce qui reste non couvert après cette session** : le logiciel `xvp`
lui-même (`xvpsource/xvp`, le seul « serveur » — en réalité un proxy —
connu qui implémente réellement cette extension), non installé ici ;
valeur ajoutée incertaine de l'installer spécifiquement pour ce fork vu
son adoption réduite aujourd'hui (dernière activité GitHub ancienne,
usage historiquement lié à Xen) — à confirmer avant d'y investir du
temps, plutôt que de construire sur l'hypothèse que ce serait
immédiatement utile ; le comportement d'un autre serveur VNC quelconque
(non-TigerVNC) face à un message-type 250 inconnu, qui pourrait différer
(silence plutôt que fermeture) — non vérifié, seule l'implémentation
TigerVNC a été testée ici.
