# Session 12 — 2026-09-10

## Session 2026-09-10 : WebSockets, `listen()` — topologie « reverse » complète testée contre un vrai `websocat`, `websockify` confirmé structurellement incapable de ce rôle

Dernier point « 🟢 Faible » directement testable dans ce sandbox (les
autres demandent soit un vrai serveur 3.3 authentique, soit un vrai
NAT/pare-feu externe, soit une confirmation de valeur avant d'investir
du temps — voir `docs/features-backlog.md` § « Prochaines étapes
suggérées ») : la topologie « reverse » complète de
`listen(websocket=True)`, explicitement laissée non couverte depuis la
session du 2026-09-04 (`docs/sessions/session-04-2026-09-04.md`), qui
avait testé le format RFC 6455 côté serveur contre un vrai client
WebSocket tiers (bibliothèque Python `websockets`) mais pas encore
contre un vrai *proxy* relayant une connexion TCP entrante vers une
connexion WebSocket sortante — le schéma de déploiement réellement visé
par ce paramètre.

**Première étape : vérifier `websockify` pour de vrai, plutôt que de
répéter l'hypothèse de la session du 2026-09-04.** Le code contenait
déjà un commentaire suggérant `websockify LISTEN_HOST:LISTEN_PORT
--wait` côté proxy. Installé (`pip install websockify`, PyPI, dans un
venv dédié) et exécuté réellement dans ce sandbox :

```
$ websockify 127.0.0.1:19999 --wait
websockify: error: no such option: --wait
$ websockify 127.0.0.1:19999
websockify: error: Too few arguments
```

`--wait` n'est même pas une option reconnue par la version actuelle, et
sans elle, une seule adresse échoue faute de cible. Plus fondamentalement,
`websockify --help` confirme que **cet outil ne peut structurellement pas
jouer ce rôle** : ses adresses d'ÉCOUTE (`source_port`, `--unix-listen`)
sont toujours WS/HTTP, ses CIBLES toujours TCP, socket Unix
(`--unix-target`) ou sous-processus (`-- WRAP_COMMAND_LINE`) — jamais
l'inverse. `websockify` « websocket-ifie » un service TCP existant pour
un client WS (typiquement un navigateur via noVNC) ; il ne sait pas
faire l'inverse (accepter du TCP brut et ressortir en WS sortant), qui
est précisément ce que demande `listen(websocket=True)` pour ce cas
d'usage. Ce commentaire était donc une erreur de documentation dans le
fichier livré — corrigée cette session (voir plus bas).

**Outil qui convient réellement : `websocat`.** Binaire officiel
précompilé (`websocat.x86_64-unknown-linux-musl`, version `1.14.1`,
`musl 1.2.5`) téléchargé depuis les releases GitHub du projet
(`github.com/vi/websocat`, outil Rust indépendant de ce fork et de
`websockify`, connu comme « le netcat des WebSockets »). Son mode
« adresses avancées » propose exactement l'adressage manquant :
`tcp-listen:HOST:PORT` (écoute TCP brute) comme première adresse et
`ws://HOST:PORT/` (client WebSocket sortant) comme seconde — pour
chaque connexion TCP acceptée, `websocat` initie une vraie connexion
WebSocket sortante et relaie les octets dans les deux sens.

**Protocole de test.**

```
[script « serveur VNC distant » fabriqué à la main, TCP brut]
    --TCP-->
[websocat --binary tcp-listen:127.0.0.1:18600 ws://127.0.0.1:18500/]
    --WebSocket réelle (RFC 6455)-->
[listen(host='127.0.0.1', port=18500, websocket=True)]
```

Le script « serveur distant » (même construction que les tests
`listen()` précédents — ProtocolVersion/Security-None/SecurityResult/
ServerInit fabriqués à la main octet par octet, cf. `Client.create()`)
se connecte en TCP brut au port d'écoute de `websocat`, PAS au port de
`listen()` : c'est `websocat` seul qui transforme cette connexion TCP
en une vraie poignée de main + trames WebSocket vers notre serveur.

**Résultat : succès de bout en bout.** `Client` obtenu par
`listen(websocket=True)` à travers ce pont entièrement réel :
`width=800`, `height=600`, `name='Serveur VNC factice (reverse WS via
websocat reel)'`, `protocol_version=(3, 8)` — valeurs strictement
conformes à celles envoyées par le faux serveur, prouvant que la
poignée de main WebSocket côté serveur (`_ws_handshake_server()`) et le
dévetissement de trame (`_ws_pump()`) fonctionnent correctement face à
une implémentation WebSocket cliente tierce et indépendante, aussi bien
quand elle parle directement à `listen()` (2026-09-04, bibliothèque
`websockets`) que lorsqu'elle est produite par un vrai proxy générique
(2026-09-10, `websocat`) plutôt que par notre propre code des deux
côtés. Seul avertissement relevé côté `websocat`, sans effet sur ce
test à une seule connexion : *"serving multiple clients without
--exit-on-eof (-E) or with -U option is prone to socket leak in this
websocat version"* — une limite connue de `websocat` en usage
multi-clients répétés, pas un problème d'`asyncvnc2`.

**Corrections apportées à `asyncvnc2.py` : docstrings/commentaires
uniquement, zéro ligne de code exécutable modifiée** (diff complet
contre le fichier livré vérifié — seuls 3 blocs de texte de
documentation ont changé) :

1. Docstring de `listen()` : mentionnait « testé contre un vrai
   `websockify` en mode "reverse" » — jamais vrai, corrigé pour
   distinguer clairement les deux vérifications réelles (2026-09-04 vs
   `websockets`, 2026-09-10 vs `websocat`) et prévenir explicitement
   que `websockify` ne convient pas pour ce rôle précis.
2. Commentaire dans le corps de `listen()` (juste avant l'appel à
   `_ws_wrap_connection_server()`) : contenait l'exemple d'invocation
   `websockify LISTEN_HOST:LISTEN_PORT --wait` qui échoue à l'exécution
   (voir ci-dessus) — remplacé par une explication vérifiée de la
   limite structurelle de `websockify` et l'invocation `websocat` réelle
   qui fonctionne.
3. Docstring de `_ws_handshake_server()` : mentionnait `websockify`
   comme exemple « typique » de proxy appelant — corrigé de la même
   façon.

**Non-régression vérifiée** dans ce sandbox après les corrections :

**Ce qui reste non couvert après cette session** : cette vérification
reste faite en loopback, à l'intérieur de ce même sandbox — elle
confirme que le format RFC 6455 et l'orchestration `listen()` sont
corrects face à un vrai relais TCP→WS indépendant, mais ne teste pas un
vrai serveur VNC distant se reconnectant à travers un vrai NAT/pare-feu
externe (ce point reste distinct et toujours ouvert, voir
`docs/features-backlog.md` § « Prochaines étapes suggérées », point
« Reconnexion inversée (`listen()`) : test réel... à travers un vrai
NAT/pare-feu »). Comportement de `websocat` au-delà d'une seule
connexion (voir l'avertissement `--exit-on-eof`/`-U` relevé plus haut)
non exploré, hors sujet pour ce test.
