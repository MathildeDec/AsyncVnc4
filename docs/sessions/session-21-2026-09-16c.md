## Ré-examen de SASL (20), écarté trop vite en session 20

La session 20 avait écarté SASL en bloc, au motif qu'« implémenter ne
serait-ce qu'un seul mécanisme demanderait une bibliothèque SASL tierce
(`cyrus-sasl`, souvent une infrastructure Kerberos pour `GSSAPI`) ». En
relisant `rfbproto.rst` (section « SASL ») plus attentivement pour cette
session, ce raisonnement s'avère correct pour `DIGEST-MD5`/`GSSAPI`/
`CRAM-MD5`, mais **pas pour tous les mécanismes SASL sans exception** :

- Le tramage RFB lui-même (mechlist, client-start, server-start,
  client-step, server-step) est un protocole générique de messages
  longueur-préfixée, **entièrement documenté indépendamment de toute
  bibliothèque SASL** — `sasl_client_start`/`sasl_client_step` n'y sont
  mentionnés que comme la source *habituelle* du contenu opaque, pas
  comme une exigence de format.
- `PLAIN` (RFC 4616) et `ANONYMOUS` (RFC 4505) sont chacun définis par
  leur propre RFC autonome, sans aucun échange défi-réponse ni état à
  maintenir entre plusieurs mécanismes — le contenu de `clientout-data`
  pour ces deux mécanismes se calcule directement, sans bibliothèque
  tierce, exactement comme le reste de ce fichier calcule lui-même ses
  formats DES/AES-EAX sans dépendre d'une bibliothèque VNC complète.

Ce n'est donc pas un mécanisme « générique SASL » qui est implémenté ici,
mais deux mécanismes SASL précis, choisis parce qu'ils sont les seuls
pour lesquels le tramage RFB documenté suffit intégralement — même
principe de refus explicite plutôt que d'implémentation partielle
déguisée que pour ZYWRLE ou le type de sécurité 18 (voir
`docs/features-backlog.md`), appliqué ici dans l'autre sens : au lieu de
refuser tout SASL par prudence globale, seuls les mécanismes non
documentés indépendamment d'une bibliothèque sont refusés, mécanisme par
mécanisme, au moment de la négociation (`_sasl_negotiate()` lève une
`ValueError` explicite listant les mécanismes offerts non pris en
charge).

## Implémentation

### `_sasl_negotiate()` (nouvelle fonction, `asyncvnc2.py`)

Suit le tramage `rfbproto.rst` section « SASL » à la lettre :

1. Lecture de `mechlist-length` (`U32`) + `mechlist-string` (liste de
   noms de mécanismes séparés par des virgules) ;
2. Choix du mécanisme : `PLAIN` en priorité si offert et si
   `username`/`password` sont fournis (mécanisme authentifié) ; sinon
   `ANONYMOUS` si offert ; sinon `ValueError` listant les mécanismes
   offerts (aucun n'est pris en charge sans bibliothèque SASL réelle) ;
3. Construction de `clientout-data` :
   - `PLAIN` (RFC 4616) : `authzid NUL authcid NUL passwd`, `authzid`
     laissé vide (pas de délégation d'identité) ;
   - `ANONYMOUS` (RFC 4505) : message de trace optionnel — le nom
     d'utilisateur fourni s'il y en a un, sinon chaîne vide (les deux
     sont valides selon la RFC) ;
4. Envoi du « SASL client start message » (`mechname-length` + nom +
   `clientout-length` + `clientout-data`, complété d'un octet `NUL` de
   bourrage comme l'exige la spec pour préserver la distinction
   NULL/chaîne-vide) ;
5. Lecture du « SASL server start message » (`serverout-length` +
   `serverout-data` + `complete-flag`) ;
6. `complete-flag != 1` → `ValueError` explicite (`PLAIN`/`ANONYMOUS`
   sont tous deux à une seule étape ; un `complete-flag` à 0 indiquerait
   un serveur attendant un `SASL client step message` non prévu par ces
   deux mécanismes — refusé plutôt que deviné, même principe que pour
   ZYWRLE) ;
7. Pas de `sasl_encode`/`sasl_decode` implémenté : ni `PLAIN` ni
   `ANONYMOUS` ne négocient de couche de confidentialité/intégrité
   (SSF nul par construction pour ces deux mécanismes, RFC 4422) — ce
   n'est pas une limite de cette implémentation mais une propriété des
   mécanismes eux-mêmes, documentée dans la docstring de la fonction.

### Intégration dans `Client.create()`

- `20` ajouté en toute dernière position de l'ordre de préférence de
  négociation, après `113` (MSLogonII) : `PLAIN` envoie le mot de passe
  directement sur le fil sans aucune couche de chiffrement propre à ce
  type de sécurité (contrairement aux sous-types VeNCrypt `...SASL` de
  la spec — `TLSSASL`/`X509SASL` — qui enveloppent SASL dans un TLS déjà
  négocié, hors périmètre de cette session), donc moins sûr même que la
  clé Diffie-Hellman 64 bits de MSLogonII.
- Un unique appel `await _sasl_negotiate(reader, writer, username,
  password)` sous `if auth_type == 20:`, juste avant le bloc
  `SecurityResult` déjà existant (inchangé — SASL, comme les autres
  types de sécurité 3.8, envoie toujours un `SecurityResult` classique
  après négociation, pas de cas particulier 3.3/3.7 comme pour `None`).

## Vérification

**Aucun serveur SASL de référence installable dans ce sandbox** (même
limite déjà documentée pour MSLogonII/Ultra(LZO) en session 20) — la
bibliothèque `cyrus-sasl` elle-même n'est pas nécessaire ici puisque
`PLAIN`/`ANONYMOUS` sont calculés directement, mais aucun serveur VNC
réel n'annonce ce type de sécurité dans ce sandbox pour autant.

7 tests unitaires ajoutés (`SaslNegotiateTests`, round-trip auto-cohérent
fabriqué à la main, même méthode que pour MSLogonII) :
- `PLAIN` choisi en priorité quand offert avec des identifiants, format
  du message vérifié octet par octet contre RFC 4616 ;
- `ANONYMOUS` utilisé quand `PLAIN` n'est pas offert, message de trace =
  nom d'utilisateur fourni ;
- `ANONYMOUS` avec message vide quand aucun nom d'utilisateur n'est
  fourni ;
- `ValueError` si aucun mécanisme pris en charge n'est offert (`DIGEST-
  MD5,GSSAPI`), aucune écriture socket avant l'échec ;
- `ValueError` si la `mechlist-string` est vide ;
- `ValueError` si seul `PLAIN` est offert mais sans identifiants (et
  `ANONYMOUS` absent) ;
- `ValueError` si `complete-flag` vaut 0 (échange multi-étapes non
  supporté).

Suite complète rejouée : **50/50 tests au vert** (43 précédents + 7
nouveaux), `ruff check` toujours à 0 signalement, `ruff format --check`
toujours idempotent (le fichier de test a nécessité un passage
`ruff format` après l'ajout des nouveaux tests — purement des retours à
la ligne sur des expressions multi-lignes, aucun changement de contenu).
`Client.create()` — signature publique inchangée (aucun nouveau
paramètre : `_sasl_negotiate()` réutilise `username`/`password` déjà
acceptés, comme VeNCrypt Plain et MSLogonII avant elle).
